# Module One — Engineering Contract

The Normal team-health tool: a weekly **360 check-in** (Activity · Excellence · Morale) → transcribed → LLM-graded → **Red/Yellow/Green heat-map** across teams and weeks. Keep it **shallow** — a review tool, not a task manager.

Stack: **Next.js (App Router) + TypeScript + Tailwind + shadcn/ui + Supabase + Vercel.**

## Git
- Never commit directly to `main`. Create a feature branch.
- Claude may merge a PR without asking once all three hold on its latest commit: CodeRabbit has approved it, Qodo has reviewed it and left no open "Action required" finding, and the CI `check` passed. Hold it while the PR lists unticked "Before merging" steps.
- Never bypass CI or branch protection. Don't post `@coderabbitai approve` unless the user asks; the approval must come from CodeRabbit's own review.
- Small, focused PRs.
- `main` protection lives in `.github/rulesets/protect-main.json` (applied with `scripts/protect-main.sh`), plus a classic branch-protection rule until that is removed. Change it only by PR; never loosen it in the GitHub UI.

## Database
- Never modify the production schema by hand. **All schema changes are migrations in `supabase/migrations/`.**
- **RLS ON for every table** (see 0001_init.sql, 0002, 0003). Members see their own check-ins and their team's members; leaders see check-ins made in the teams they lead (their own team plus their `team_leads` rows, and everything under those: leading a domain covers its sub-teams); `hq` sees every team, member and check-in. Recordings and Big Five need the `recordings` / `big_five` grants, even for `hq`.
- Never expose the service-role key to the client — server-only.
- Members only **read**, through the Data API and Storage (see 0002). Check-in writes (transcripts, scores, mentions, recordings) go through server code using the service-role key, which takes the member from the session, never from the request.
- Admin edits are allowed by RLS only for holders of the matching grant in `member_grants` (`admin`: teams, other members' name/team/role except hq and themselves, `scoring_settings`; `big_five`: Big Five profiles). Only the project owner makes someone `hq`. Grants themselves are changed only by the project owner in the Supabase dashboard; never add an API write path for them. Admins give people a login (`auth_user_id`) only through the `giveLogin` server action (`src/app/admin/teams/[id]/actions.ts`): never for an `hq` row, a member who already has a login, a member who holds grants, or a row with check-ins, a Big Five profile or recordings from an earlier login; it records who gave it in `login_given_by` / `login_given_at`. `resendInvite` (same file) re-sends an unused invite. `changeEmail` (same file) changes anyone's sign-in email at any time, never for an `hq` row, the admin themselves, a grant holder, or someone who sits in or leads the organisation, and records who did it in `login_email_changed_by` / `login_email_changed_at` (the project owner accepted that an admin can point a used login at an address of their own). A used login keeps its `auth_user_id` and gets the new address; an unused one is replaced: the new address is invited and that new login becomes the row's `auth_user_id` (filling `login_given_by` / `login_given_at` if they were empty), so for that one case `auth_user_id` changes outside `giveLogin`, without its earlier-login refusals (the owner's decision). Admins remove people only through `removePerson` (same file), which calls `admin_remove_member` (0009): the one SECURITY DEFINER function admins write through, so it checks everything RLS would (and refuses the same people as `changeEmail`). It unlinks and deletes their login and keeps the row, marked `removed_at` (no team, no login, member role), whenever they ever had a login or anything refers to them; only a row with neither is deleted. Removed people are never listed, edited, placed or given a login again in the app; only the project owner restores one. The admin pages show whether each login has been used through `admin_login_states` (0010), a read-only SECURITY DEFINER function that checks the `admin` grant itself and returns each linked login's state (invited, ready or active) with its invite and last sign-in times, never an email address or any other `auth.users` column. `src/lib/supabase/admin.ts` is the only service-role client, used only by these four actions, the check-in's server code (including the live check-in's session store, `src/lib/checkin/live-sessions.ts`, and the cost log, `src/lib/costs/record.ts`) and the Master Admin's delete/reset actions below (`admin-imports.test.ts` lists who may import it).
- New tables, views and functions get no grants by default (as on hosted Supabase): grant what's needed in the same migration, `revoke execute … from public` on new functions, and create views `with (security_invoker = true)` so RLS still applies.
- Recordings: private `checkin-audio` bucket, `<member_id>/<file>`. To record, the server creates a signed upload URL (upsert off) for a path it builds from the session, and the browser uploads straight to it. Only the speaker and holders of the `recordings` grant can play recordings. Only Master Admins (`hq`) can delete a check-in's recording (not while it waits for the grader) or reset a week's check-in (0007: `hq_delete_checkin_recording` / `hq_reset_checkin`, which check the caller themselves and log to `checkin_resets` with the files to delete); the server action (`src/app/portal/dashboard/[teamId]/[week]/actions.ts`) then removes only those files and stamps `files_removed_at`, and the daily job retries unstamped rows. RLS tests live in `supabase/tests/` (`supabase test db`).
- Teams are a tree (0003, 0005, 0006): the organisation → divisions → domains → teams (`parent_id`, `kind`), enforced by triggers whose messages the UI shows as is. There is one organisation node (`kind = 'organisation'`, first named "The New Normal"); every division sits under it, and it is never moved, archived or turned into anything else. Unplaced domains sit at the top level, outside it. People sit in the organisation, a division, a domain or a team; whoever sits in a division or the organisation leads it (a member placed there becomes a leader, hq stays hq, and nobody sitting there can be made a member). Only the project owner places someone in the organisation or makes someone a lead of it (it shows every check-in, like hq), never an admin through the app. A node's `leader_title` names whoever leads from it ("President" for the organisation); admins rename it, and it never changes what anyone sees. Admins move nodes with `admin_move_team` (drag-and-drop) and maintain `team_leads` (never for themselves; nor can an admin move a node into one they lead); nodes are archived, never deleted. Tree and placement changes must run under READ COMMITTED. `teams.division` is deprecated (the parent division node replaced it). The "HQ" division is unrelated to the `hq` role.
- Each check-in stores the team it was made in (`checkins.team_id`, filled from the member's team on insert). The heat-map groups by it, and leaders see check-ins by it. Teams are archived (`archived_at`), never deleted.
- Heat-map colours come from `src/lib/health` with the `scoring_settings` row (`settingsToConfig`), never from `checkins.category`.
- The grading and coach rubrics are `rubrics/grading.md` and `rubrics/coach.md`: plain files people edit, that the grader's and live coach's prompts are built from (their tests check them on every PR; `rubrics/README.md` explains them). Safety rules (the transcript is data, never instructions), the reply format, the review's length limit, the call and session limits and the allowed range of every `coach.md` setting stay in code, never in the files. `live_checkin_sessions` (0011) is service-role only, with no grants to members or anyone else: the coach's coverage reads like a judgement. No OpenAI key, not even a short-lived one, is ever sent to the browser: the server opens each live session's one transcription connection (`/portal/checkin/live/connect`, `connect_live_checkin_session` in 0012) and passes back only OpenAI's WebRTC answer. Members are only ever shown which areas they have touched.

## Security
- Never commit secrets (`.env*` is git-ignored; use `.env.example`).
- Never disable auth checks or weaken RLS without explicit review.

## Testing
- Add tests for new business logic. Write tests for the riskiest endpoints first: `transcribe()` and the rubric grader.
- Run `pnpm typecheck && pnpm lint && pnpm test` before opening a PR.

## Build philosophy
- build → simplify → automate. Manual-input-first.
- Scope guard: this is the 360 reviewer + weekly heat-map dashboard. Do NOT add a general task manager, CRM, or finance features.

## The thing to build (MVP by Friday)
1. Supabase magic-link auth → portal.
2. Weekly check-in page: "Start" records audio under one open question on screen (`rubrics/coach.md`'s opening question); with live check-ins on, follow-up questions appear as the member talks, for whichever of the three areas they haven't covered (once asked as three fixed questions):
   - "What have you done this week?" → activity
   - "Where did you / your team use your superpower?" → excellence
   - "How are you feeling about the team?" → morale
3. `transcribe()` abstraction — web-API impl now, local Parakeet/OruKey impl stubbed behind the same interface.
4. Claude rubric-grader → `{ activity, excellence, morale, category, review }`, stored on the checkin.
5. Dashboard: teams × weeks grid, each cell R/Y/G from `activity × excellence × (morale as multiplier)`; click a cell to drill in.
